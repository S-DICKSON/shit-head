These tests use `page.routeWebSocket()` to mock the WebSocket server and pre-seed the UI into specific game states. This avoids needing real multi-player coordination.

**CRITICAL:** `routeWebSocket` is Chromium-only. Every test that uses WS mocking MUST include:
```typescript
test.skip(({ browserName }) => browserName !== 'chromium', 'WS mocking requires Chromium');
```
The mobile projects spread `devices['iPhone SE']` and `devices['iPhone 14']` which use `defaultBrowserType: 'webkit'`, so WS-mocked tests will skip on mobile-375 and mobile-390. The other 4 projects (tablet, laptop, desktop, discord-iframe) default to chromium. This is acceptable.

**CRITICAL — Message Protocol:** The client's `useGameSocket.ts` has NO handler for a `game-view` message type. The actual protocol uses:
- `room-created` — sets `playerId` and `roomState` (triggers router navigation to `/room/CODE`)
- `game-dealt` — sets `gameView` with FLAT fields (not nested under a `view` key)

The `game-dealt` message must match `gameDealtSchema` from `@shit-head/shared`:
```typescript
{
  type: 'game-dealt',
  phase: 'swapping' | 'playing',
  hand: Card[],
  faceUp: Card[],
  faceDownCount: number,
  opponents: OpponentView[],
  drawPileCount: number,
  discardPile: Card[],
  currentPlayerIndex: number,
  dealerIndex: number,
  firstTurn: boolean,
}
```

**CRITICAL — Message Sequencing:** The navigation flow is:
1. Client sends `create-room` message
2. Mock responds with `room-created` -> this sets `roomState`, router navigates to `/#/room/CODE`
3. Lobby.vue mounts and registers its `onMessage` handler (which listens for `game-dealt` -> `router.push('/game')`)
4. Only AFTER Lobby has mounted should the mock send `game-dealt`

If `room-created` and `game-dealt` are sent simultaneously (back-to-back), the `game-dealt` arrives BEFORE Lobby.vue mounts and registers its `onMessage` handler. Lobby's handler never sees the message, and navigation to `/game` never happens. The test stalls.

**Concrete sequencing strategy:** Track message count from the client. The first client message is `create-room`. After sending `room-created` in response, do NOT immediately send `game-dealt`. Instead, wait for a SECOND client message (the Lobby may send `start-game` or heartbeat) OR use a delay. The most reliable approach is:

```typescript
let messageCount = 0;
ws.onMessage(rawMsg => {
  messageCount++;
  const msg = JSON.parse(rawMsg as string);
  if (msg.type === 'create-room') {
    ws.send(JSON.stringify({ /* room-created */ }));
    // Do NOT send game-dealt here — Lobby hasn't mounted yet
  }
  // On any subsequent message (heartbeat/ping, start-game, etc.),
  // or if no second message arrives, use a setTimeout fallback
});
// Fallback: send game-dealt after a short delay to ensure Lobby has mounted
// The test should also call page.waitForURL to confirm lobby navigation before proceeding
```

Actually, the simplest reliable approach: In the TEST code (not the mock), after `room-created` navigates to lobby, use `await page.waitForURL(/\/#\/room\//)` to confirm Lobby has loaded, THEN trigger the `game-dealt` message from the mock. To do this, store a reference to the mock's `ws` object and call `ws.send()` from the test body after the waitForURL:

```typescript
async function setupGameMock(page: Page, phase: 'swapping' | 'playing') {
  let mockWs: { send: (msg: string) => void } | null = null;

  await page.routeWebSocket('**/game-ws**', ws => {
    mockWs = ws;
    ws.onMessage(rawMsg => {
      const msg = JSON.parse(rawMsg as string);
      if (msg.type === 'create-room') {
        ws.send(JSON.stringify({
          type: 'room-created',
          playerId: 'test-player-1',
          room: {
            code: 'TEST01',
            status: 'playing',
            players: [
              { id: 'test-player-1', nickname: 'Player1', isHost: true, isConnected: true },
              { id: 'test-player-2', nickname: 'Player2', isHost: false, isConnected: true },
            ],
            hostId: 'test-player-1',
            minPlayers: 2,
            maxPlayers: 4,
            roundTime: 45,
          }
        }));
      }
    });
  });

  // Return a function to send game-dealt AFTER lobby has loaded
  return {
    sendGameDealt: () => {
      mockWs!.send(JSON.stringify({
        type: 'game-dealt',
        phase,
        hand: [ /* cards */ ],
        faceUp: [ /* cards */ ],
        faceDownCount: 3,
        opponents: [ /* opponents */ ],
        drawPileCount: 30,
        discardPile: phase === 'playing' ? [{ kind: 'standard', rank: '6', suit: 'spades' }] : [],
        currentPlayerIndex: 0,
        dealerIndex: 0,
        firstTurn: phase === 'playing',
      }));
    }
  };
}
```

Then in each test:
```typescript
test('renders swap phase UI', async ({ page, browserName }) => {
  test.skip(browserName !== 'chromium', 'WS mocking requires Chromium');
  const { sendGameDealt } = await setupGameMock(page, 'swapping');
  // Navigate and create room
  const landing = new LandingPage(page);
  await landing.goto();
  await landing.fillNickname('Player1');
  await page.getByRole('button', { name: /Create New Room/i }).click();
  // Wait for lobby to load (Lobby.vue has mounted and registered its onMessage handler)
  await page.waitForURL(/\/#\/room\//);
  await page.waitForTimeout(100); // Brief pause for Lobby's onMessage registration
  // NOW send game-dealt — Lobby's handler will catch it and navigate to /game
  sendGameDealt();
  // Wait for game screen
  await page.waitForURL(/\/#\/game/);
  // ... assertions
});
```

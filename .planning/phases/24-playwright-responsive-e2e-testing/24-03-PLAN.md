These tests use `page.routeWebSocket()` to mock the WebSocket server and pre-seed the UI into specific game states. This avoids needing real multi-player coordination.

**CRITICAL:** `routeWebSocket` is Chromium-only. Every test that uses WS mocking MUST include:
```typescript
test.skip(({ browserName }) => browserName !== 'chromium', 'WS mocking requires Chromium');
```
This means these tests will only run on the 4 Chromium-based viewport projects (mobile-375, mobile-390, laptop-1280, desktop-1920) and skip on tablet-768 and discord-iframe-460 IF those are not Chromium-based. Check the playwright.config.ts — if all 6 projects use the default Chromium browser (no `use: { ...devices[...] }` with WebKit), then the skip is a no-op and all 6 run. The mobile projects spread `devices['iPhone SE']` and `devices['iPhone 14']` which use `defaultBrowserType: 'webkit'` — so these tests WILL be skipped on mobile projects. This is correct behavior.

Actually, re-check: `devices['iPhone SE']` has `defaultBrowserType: 'webkit'` only when you use `use: { ...devices['iPhone SE'] }` in a project WITHOUT specifying a browser. Since the projects in the config do NOT specify a `use.browserName` or a `use.channel`, Playwright uses the device's `defaultBrowserType`. iPhone SE = webkit. iPhone 14 = webkit. So WS-mocked tests will skip on mobile-375 and mobile-390. The other 4 projects (tablet, laptop, desktop, discord-iframe) default to chromium. This is acceptable — mobile viewport testing for these screens is less critical than verifying the game UI renders at all.

If you want all 6 projects to use Chromium, override by adding `browserName: 'chromium'` to each project's `use` block in the config. But this contradicts the device emulation purpose. Leave as-is and accept the skip.

async function mockSwapPhaseState(page: Page) {
  await page.routeWebSocket('**/game-ws**', ws => {
    // Send initial connection acknowledgment then room + game state
    ws.onMessage(rawMsg => {
      const msg = JSON.parse(rawMsg as string);
      if (msg.type === 'create-room') {
        // 1. Send room-created with playerId
        ws.send(JSON.stringify({
          type: 'room-created',
          playerId: 'test-player-1',
          room: {
            code: 'TEST01',
            status: 'playing',
            players: [
              { id: 'test-player-1', nickname: 'Player1', isHost: true, isConnected: true }
            ],
            hostId: 'test-player-1',
            minPlayers: 2,
            maxPlayers: 4,
            roundTime: 45,
          }
        }));
        // 2. Send game-view with swap phase
        ws.send(JSON.stringify({
          type: 'game-view',
          view: {
            phase: 'swapping',
            hand: [
              { kind: 'standard', rank: 'K', suit: 'hearts' },

Important: Study `useGameSocket.ts` to understand what messages the client expects and how `roomState` and `gameView` refs are set. The mock must send messages in the format the composable expects (it listens for `room-created`, `room-updated`, `game-view` etc.). Study the actual message handler flow carefully and replicate it.
